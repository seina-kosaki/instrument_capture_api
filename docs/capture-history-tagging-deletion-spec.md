# 撮影履歴・タグ付け操作・画像削除仕様

## 目的・対象

撮影後のタグ入力を中心→端点A→端点Bの順で進めやすくし、撮影履歴から誤撮影を削除できるようにする。既存の撮影・タグ付け画面と、それを支えるAPI・保存データを対象とする。

| 項目 | 決定 |
|---|---|
| AI開発 | いいえ。学習・評価・推論は対象外 |
| フロントエンド | Yes — 既存React / TypeScript |
| バックエンド/API | Yes — 既存Python / FastAPI |
| DB | 既存のセッション単位SQLiteを使用。画像削除時に画像および関連行を削除する |

## タグ入力の動作

- 画像上で中心を決定した後、選択中の点種別を端点Aへ自動で切り替える。
- 端点Aを決定した後、端点Bへ自動で切り替える。
- 端点Bを決定した後、中心へ戻し、現在のタグ選択を解除する。次の画像クリックで次のタグを入力できる。
- 対象は現在のタグ付け画面にある点種別選択と画像クリックであり、座標の正規化、タグの検証・保存、点の編集など既存動作は維持する。端点は既存どおり任意入力とし、タグ保存時に必須化しない。

## 撮影履歴からの削除

- 撮影履歴の各画像（未タグ・タグ済みの両方）に削除操作を設ける。削除前に確認を表示し、確認後に対象画像だけを削除する。
- 成功時は履歴から対象を除き、履歴件数を更新する。対象が現在表示中の画像なら、その画像とタグ編集状態も画面から解除する。失敗時は履歴項目を維持し、エラーを表示する。
- 現在の履歴は撮影画面が保持する当該セッション内の撮影画像一覧である。履歴を過去セッション横断に拡張したり、新たな履歴取得APIを追加したりしない。
- 削除は画像単位で行い、セッション・宣言・同じセッションの他画像は削除しない。

## 入出力・API概要

履歴表示には撮影APIの応答で得た画像情報を使い、選択した画像のタグを取得して編集する。フロントエンドとAPIの既存構成・言語を維持する。APIの詳細なデータ項目は[撮影画像API契約](./contracts/capture-images.md)に従う。

| API | 用途・入力 | 主な出力／ユーザーに見える状態 |
|---|---|---|
| `POST /declarations/{declaration_id}/capture` | 宣言に対する撮影。パスに宣言ID、リクエストボディなし | `ImageOut`（画像ID、撮影時刻、画像サイズ・形式、タグ状態、ファイルURL、任意の深度パス等）。画面は撮影画像をタグ付け対象および履歴に加える |
| `GET /images/{image_id}/file` | タグ付け中画像のファイル取得 | 画像バイナリ。画像表示に使用 |
| `GET /images/{image_id}/tags` | 履歴画像を選択したときのタグ取得 | 画像に属するタグ配列。器具ID、点座標（x/y/status）、可視性等。画面は取得した点を編集状態にする |
| `PUT /images/{image_id}/tags` | タグ保存。`hints` 配列（器具ID、可視性、中心・端点A/B座標、遮蔽等）と任意の `tagged_by` | 保存されたタグと検証結果。画像はタグ済みとなり、履歴にもタグ済み状態を表示 |
| `DELETE /images/{image_id}` | 履歴から対象画像を削除。リクエストボディなし | 成功時 `204 No Content`。対象なしは既存APIの `404`。成功時に対象を履歴から除く |

タグ座標は既存契約どおり画像内の0〜1正規化値である。タグ点の順序変更だけではAPIスキーマを変更しない。画像削除APIの契約と削除対象は上記契約書に明記する。

## 削除対象の保存データ

既存実装では、`IC_DATA_DIR`（既定 `shared_data/`）以下に日付・セッション単位のバンドルを保存し、画像メタデータの正本を各バンドルの `metadata.sqlite3` とする。`images.path` と `images.depth_path` に記録された実パスを使い、次の対象を画像ID単位で削除する。

| 種別 | 保存場所・SQL項目 | 削除要件 |
|---|---|---|
| RGB原画像 | `YYYY-MM-DD/{session_id}/raw/` 以下。実ファイル名・拡張子は `images.path` | 対象画像のファイルを削除 |
| 深度画像 | 取得された場合、同じバンドルの `depth/` 以下。実ファイル名・拡張子は `images.depth_path`（PNGまたはTIFF） | パスが設定されている場合はファイルを削除 |
| タグデバッグ画像 | タグ保存時に生成される `YYYY-MM-DD/{session_id}/debug/{image_id}.jpg`（設定により未生成の場合あり） | 存在する対象ファイルを削除 |
| 画像メタデータ | バンドル内 `metadata.sqlite3` の `images` 行（`image_id`、`path`、`depth_path`、タグ状態等） | 対象行を削除 |
| タグ | 同DBの `hints` 行（`image_id` に紐づく器具・個体番号・点情報） | 対象画像に属する全行を削除 |
| 注釈リビジョン | 同DBの `annotation_revisions` 行（`image_id` と `session_id` で対象画像に紐づく） | 行が存在する場合は削除 |

削除後も `sessions`、`declarations`、他画像の行・ファイル、およびセッション単位の `session_splits` は保持する。現行スキーマには画像とタグ等を結ぶ外部キー制約がないため、画像IDに紐づく行を明示して除去する。セッション全体の削除APIは本仕様の対象外。

## 制約・対象外

- 撮影履歴の範囲、カメラ制御、タグの意味・検証、画像形式、既存の撮影・保存先を変更しない。
- 新しい履歴一覧API、AI機能、セッション削除UI、他セッションの画像削除は追加しない。
- 外部APIの契約は `docs/contracts/capture-images.md` で管理する。既存の `DELETE /images/{image_id}` を利用し、画面操作の追加に伴う不要なAPI重複は作らない。

## 受け入れ条件

1. 中心決定後は端点A、端点A決定後は端点B、端点B決定後は中心が自動選択される。
2. 端点B決定後はタグ選択が解除され、次の画像クリックで新しいタグを入力できる。既存の任意端点と保存・検証動作は維持される。
3. 撮影履歴の未タグ・タグ済み画像のどちらにも削除操作があり、確認前にはAPI削除を実行しない。
4. 確認後の成功時に対象だけが削除され、履歴と現在の選択状態が更新される。失敗時は履歴項目を失わず、エラーが見える。
5. 削除後、対象のraw・存在するdepth/debug画像、`images`・`hints`・`annotation_revisions` の対象行が残らない。セッション・宣言・他画像は残る。
6. API成功応答は204であり、履歴UIが削除処理の完了を認識できる。タグ付け・削除以外の既存API契約は変更しない。

## 未解決事項

- `annotation_revisions` には `manifest_path` / `annotation_path` 列があるが、現行アプリにこれらのファイルを作成・管理する処理は見つからない。将来または外部処理で実ファイルが存在する場合の所有権・画像削除時の扱いは要確認。
- 日次レポート等の派生出力を画像削除に合わせて再生成する合意はない。既存の画像単位削除APIはこれらを更新しないため、再生成の要否は未確定。
- SQL行と複数ファイルの削除中にI/O障害が起きた場合の再試行・部分削除時の応答方針は未合意。成功応答時に保存データ一式が残らないことは受け入れ条件とする。
